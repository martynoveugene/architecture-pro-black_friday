# <a name="_qmphm5d6rvi3"></a>**Решение**

Критически важными с точки зрения целостности и скорости обработки данными являются те, которые были определены как primary
для чтения в предыдущем задании плюс пользовательские сессии.
То есть это:
 - данные по остаткам товаров - коллекция quantity
 - коллекция корзина carts
 - пользовательские сессии

Здесь важна целостность данных и скорость обработки.
Так же здесь важна возможность автоматического горизонтального масштабирования.

## <a name="_3bfxc9a45514"></a>**Концептуальная модель**

Необходимо использовать geo_zone в ключе партиции - тем самым запрос отправится в соответствующий региональный дата-центр.
Вторая часть ключа распределит данные равномерно внутри регионального узла.

| **Сущность** | **Partition Key**            | **Clustering Columns** | **Описание**                                                                     |
|:-------------|:-----------------------------|:-----------------------|:---------------------------------------------------------------------------------|
| quantity     | geo_zone, product_id         | product_id             | Данные об остатках лежат в конкретном регионе                                    |
| carts        | geo_zone, user_id/session_id | item_id/session_id     | Корзина привязана к региону, те самым исключается переток данных между регионами |
| session      | geo_zone, session_id         | session_id             | Такой же принцип                                                                 |
|              |                              |                        |                                                                                  |

Локальная целостность: настройка уровеня консистентности LOCAL_QUORUM. Запись быстро подтвердится внутри геозоны, а в другие регионы данные передадутся позже.

## <a name="_3bfxc9a45514"></a>**Выбор стратегии для обеспечения целостности данных**

Выбираем локальную согласованность, и допускаем, что данные между регионами синхронизируются чуть позже.

1. Hinted Handoff - нужно применить для всех сущностей, поскольку это базовый механизм который обеспечивает целостность в конечном счете.
2. Read Repair - применить на сущностях carts и session, поскольку эти данные читаются очень часто. Если найдется расхождение, актуальная версия запишется на отставший узел.
3. Anti-Entropy Repair - Сравнение всех данных на узлах. Применяем на quantity, поскольку целостность важнее скорости. Нельзя продать товар, которого нет. Важно иметь актуальный остаток товара.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Модель потока событий.
Например все чобытия сохраняются в Kafka (Товар добавлен, Заказ создан).
А потом данные актуализируются в базах, можно для каждой сущности применить свою базу. 

### **Недостатки, ограничения, риски**

1. Проблема с переносом пользователя из зоны в зону.
2. Размеры зон могут сильно отличаться
3. Затруднение в составлении глобальных отчетов по всем зонам.
