### <a name="_3bfxc9a45514"></a>**Коллекция carts**
В эту коллекцию добавляем геозону, которая будет устанавливаться при создании корзины. 

| **Поле**         | **Тип**    | **Индекс** | **Описание**                            |
|:-----------------|:-----------|:-----------|:----------------------------------------|
| _id              | ObjectId   | PK         | Уникальный идентификатор корзины        |
| user_id          | ObjectId   | FK         | Идентификатор клиента                   |
| session_id       | ObjectId   |            | Идентификатор гостевой сессии           |
| items            | Array      |            | Список заказанных товаров и их цена     |
| items.product_id | ObjectId   | FK         | Ссылка на товар                         |
| items.quantity   | int        |            | Количество                              |
| created_at       | Date       |            | Дата и время создания корзины           |
| updated_at       | Date       |            | Дата и время последнего обновления      |
| expires_at       | Date       |            | Дата и время удаления (TTL)             |
| status           | String     |            | Статус корзины active/ordered/abandoned |
| geo_zone         | String     |            | Геозона товара                          |

Основные операции:
 - Создание корзины, когда заходит гость или новый пользователь.
 - Получение текущей корзины по фильтру { session_id, status:"active" } или { user_id, status:"active" }.
 - Добавление или замена товара в корзине.
 - Удаление товара из корзины.
 - Слияние гостевой корзины в пользовательскую, если пользователь залогинится:
     прочитать гостевую { session_id, status:"active" };
     добавить её items в корзину { user_id, status:"active" };
     отметить гостевую как abandoned.
 - Отметка корзины как заказанной.


## <a name="_qmphm5d6rvi3"></a>**Решение**
Необходимо реализовать два уровня шардирования.
 - Верхний уровень - шардирование по геозонам для перенаправления запросов пользователя к ближайшей к нему геозоне.
 - Нижний уровень - шардирование внутри каждой зоны для обеспечения высокой производительности и равномерного распределения данных.

### <a name="_3bfxc9a45514"></a>**Кандидаты для шард-ключей**

На верхнем уровне выбираем диапазонное шардирование на основе геозоны. 

Пользователь будет подключаться к ближайшему инстансу АПИ по геозоне.
Таким образом геозона пользователя будет использоваться для создания Корзины, неважно залогинен ли уже пользователь или он еще гость.
Все операрации по работе с корзиной будут перенаправляться к ближайшим инстансам АПИ.
Заказы также будет храниться в своих шардах по геозоне пользователя. Таким образом история заказов пользователя будет выбираться из одной шарды БД.
Получение статуса заказа так же будет работать быстро.
Сами продукты на вернем уровне не будут шардированы, т.е. их копии будут присутсвовать во всех геозонах,
их не так много и они редко меняются, так что это допустимо. таким образом поиск и загрузка описания одного продукта будет работать быстро.
В то время как остатки продуктов - это очень часто меняющиеся данные, и для эффективной работы предлагается их вынести в отдельную коллекцию.
Есть явное требование по хранению остатка товара в каждой геозоне, таким образом нужно хранить геозону для каждого остатка 
и сделать шардирование по ней. Изменение остатка при покупке будет происходить в геозоне корзины.

Далее на нижнем уровне можно добавить хэшированное шардирование внутри каждой зоны.  
Ключ шардирования - первичный ключ коллекции, это гарантирует равномерное распределение объектов по шардам.
Для orders выбираем ключ user_id для того, чтобы все заказы пользователя попадали в один шард, для последующего поиска истории заказов.
Для products выбираем ключ _id - для равномерного распределения продуктов по шардам.
Для коллекции Остатков quantity ключ хеширования будет product_id, т.к. в рамках отдельной зоны он будет уникальным для коллекции.
Для carts выбираем ключ user_id либо session_id для равномерного распределения. 


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

Можно сделать только один из уровней шардирования. 
1. Только шардирование по геозоне.
Запросы будут распределяться на сервера близкие к пользователю. Но со скоростью обработки могут возникнуть проблемы. 
2. Только хэшированное шардирование.
Запросы будут быстро обрабатываться, но передача данных может быть затруднена из-за удаленности пользователя от сервера.

### **Недостатки, ограничения, риски**

1. Сложность организации двухуровнего шардирования.
2. Недостаток компетенций может сказаться на успехе проекта.
3. Необходим подбор множества ЦОД, которые обеспечат равномерное присутствие в зонах обслуживания.
4. Возможны задержки при репликации продуктов из-за потери связности между зонами, критичность будт зависеть от требований
по обеспечению изменения цены продукта сразу во всех зонах - это самый важный параметр продукта.
Если цены меняются часто и нужно обеспечить их быструю согласованность, то решение требует доработки.
