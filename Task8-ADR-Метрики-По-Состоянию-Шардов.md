## <a name="_3bfxc9a45514"></a>**Метрики**
В каждой метрике есть геозона и наименование шарда.

### <a name="_3bfxc9a45514"></a>**Метрики нагрузки на базу**

- Количество запросов в секунду.
должна содержать вид запроса insert, query, update, delete.

- Количество активных соединений

- Время задержки ответа (Latency)
по операциям - чтения/записи.

### <a name="_3bfxc9a45514"></a>**Метрики балансировки данных**

- Объем данных на каждом шарде

- Количество чанков на каждом шарде.

- Количество «гигантских» чанков, которые MongoDB не может разделить.

### <a name="_3bfxc9a45514"></a>**Метрики сети**

- Сетевая передача данные in/out

## <a name="_qmphm5d6rvi3"></a>**Решение**

Выявление «горячих ключей» (Hot Keys) — это поиск конкретных значений ключа шардирования,
на которые приходится непропорционально много запросов.

Необходимо иметь дашборд, где на одном графике отображаются линии метрик для всех шардов одновременно.
Если графики большинсва шардов идут примерно одинаково, а линия одного из них существенно отличается, 
то это свидетельствует о проблеме с распределением нагрузки.

### <a name="_3bfxc9a45514"></a>**Команды для выявления горячих ключей**

1. Команда, которая показывает статистику использования коллекций в реальном времени.
````
db.adminCommand("top")
````
Она показывает, какие коллекции тратят больше всего времени на чтение/запись.
Если одна коллекция активно присутствует на одном шарде и отсутствует на других — внутри неё есть горячий ключ.

2. Включить сбор данных о «медленных» или вообще всех операциях. Например — записывать операции дольше 50мс:
````
db.setProfilingLevel(1, { slowms: 50 })
````
Поиск осуществляется в коллекции system.profile на каждом шарде.
Необходимо сгруппировать запросы по полю query. Если найдется такой, что к нему привязано большое количество запросов, то значит, этот ключ «горячий».

3. Команда статус.
````
sh.status()
````
Если один из чанков помечен как Jumbo, это дает признак горячего ключа.
Jumbo chunk возникает, когда данных по одному ключу стало очень много и MongoDB не может разделить этот чанк. 

4. Анализ логов.
````
mlogfilter mongod.log --slow 100 --scan
````
Это команда для поиска запросы, которые чаще всего вызывают сканирование индексов или коллекции.

### <a name="_3bfxc9a45514"></a>**Исправление проблемы горячих ключей**

1. Hashed Sharding: Вместо поиска по диапазону использовать хэш ключа. Этот способ распределит одинаковые значения по разным шардам.
2. Compound Sharding: Добавить к текущему ключу второе поле (например, к user_id добавить order_id), чтобы сделать ключ более уникальным.
3. Прикладное кэширование: Если ключ горячий на чтение, его нужно кэшировать в Redis, чтобы запрос вообще не доходил до MongoDB.


### <a name="_3bfxc9a45514"></a>**Механизм распределения данных Zoned Tag Sharding**

Zoned Tag Sharding — это стратегия распределения данных между шардами на основе меток (тегов).
Для физических серверов хранящих шарды назначают метки зон. 
Например, в нашем случае выбираем георгафический принцип - Central, NorthWest, Siberia, Ural  ...
Метки зон - представляет собой логический уровень хранения данных.
Таким образом, несколько физических серверов будут относится к одной логической зоне.
Данным также устанавливаем теги на основании привязки пользователя к определенному региону.
У нас уже есть поле geo_zone для этого. Но если бы его не было, а была, например, область проживания пользователя,
то можно было бы определить диапазон областей, которые бы относились к географической зоне.
То есть в момент когда запрос обрабатывается mongos роутером, роутер смотрит на поле 'область' и понимает к какой
геграфической зоне он относится и понимает на сервер какой зоны перенаправить запрос. 

Таким образом, информация пользователей строго распределяется на физические серверы по географическому принципу.


### <a name="_3bfxc9a45514"></a>**Механизм автоматического перераспределения данных**

1. Встроенный баоансировщик и автоматическое деление. Это «родной» механизм MongoDB, который работает в фоновом режиме.
Балансировщик постоянно сравнивает количество чанков на каждом шарде. Если разница превышает порог, он начинает миграцию данных с перегруженного шарда на менее загруженный.
Можно задать «окна обслуживания», чтобы миграция происходила только ночью и не нагружала сеть в пик трафика.

2. Зональное шардирование - позволяет вручную или полуавтоматически связывать диапазоны данных с конкретными шардами.

3. Автомасштабирование через Terraform и Kubernetes. При достижении лимита по CPU или объему диска на текущих шардах, оператор разворачивает новый шард (реплика-сет), регистрирует его в кластере, и Balancer тут же начинает переливать туда часть данных.
4. TTL-индексы для самоочистки.  Устанавливается индекс с параметром expireAfterSeconds. MongoDB автоматически удаляет старые документы.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Сразу применять хэшированное шардирование. Вместо того, чтобы допускать появление горячего ключа,
сразу исключать его появление. При этом появляется минус - невозможность эффективно выбирать данные по диапазону.

2. Активно применять кеширование - это снимает нагрузку на БД.

3. Если перегрузка происходит на чтение, то применять чтение со вторичных реплицированных узлов.

### **Недостатки, ограничения, риски**

1. Профилирование дает доплнительную нагрузку на базу.
2. Поик горячего ключа, когда шард уже перегружен и можно не успеть предотвратить аварию.
3. Jumbo чанки может быть невозможно разделить в принципе.
